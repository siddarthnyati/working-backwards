An open Claude Skill · MIT

Working Backwards that doesn't stop at the press release.

Amazon's PR/FAQ is excellent at deciding whether to build something. By design it ends there — and that handoff is where the method dies. A PM writes a beautiful narrative, leadership nods, and then the PM opens a blank ticket and starts from zero.

This runs the whole process and terminates in vertical release slices with acceptance criteria, a dependency graph, and an importable CSV. A critic gates every stage. Every requirement cites the paragraph it came from — because a requirement that can't cite anything is a fairly precise definition of scope creep.

The rule that makes it trustworthy

      
The critic judges presence and provenance, never truth. It can
      tell whether a claim is made, whether it's specific, whether it's sourced. It cannot tell whether
      it's correct, whether the market is big enough, or whether engineering can build it.

      
So six dimensions get a real verdict — PASS, REVISE, BLOCK. Two get a
      question and an owner role, and never a verdict. A critic that returns confident judgments on
      things it cannot know is worse than no critic: it simulates a review meeting without the knowledge
      that made review meetings valuable.

    

    

      
You can override it. It goes in the log.

      
From the worked example — the critic was right by its own rule and wrong
      about the artifact. Both positions are now on the record, and a reviewer in six months can see the
      empty baselines were a decision rather than an omission.

      
OVERRIDE · Stage 5 · dimension 2 (evidence presence)

Critic said: The north star and four of five input
metrics carry [UNKNOWN] baselines and [UNKNOWN]
targets; a metric plan in which nothing is measured
asserts a measurement capability with nothing
observed behind it.

User justification: "The baseline is unknowable —
there is no confirmation field today, so the
propagation rate has never been measured. Filling it
in would mean inventing a figure. That is the
finding, not a defect in the document."

Proceeded to Stage 6. Not re-litigated.

    

  







  §3 — What it doesn't know
  
This produces the questions you take to the people who hold the context.

  
Working Backwards works at Amazon because the PR/FAQ is a meeting — fifteen minutes
  of silent reading and forty minutes of cross-functional interrogation. A solo user plus a model replaces
  the document and not the room. So the honest framing is that this is a question-generation engine, not
  an answer engine. Its output is the interrogation list, plus the scaffolding that survives their answers.

  §4 — Blockers
  
Six of them, before a single requirement was written.

  
All six came out of the FAQ stage — someone asking a hostile question, not the model
  asserting a finding. Each carries an Ask, an owner role, and a status only the user can change. There is
  no path by which the skill marks its own question resolved.

  

  
All six are high severity. That's unusual and it isn't
  inflation — each either blocks a release slice or changes what's owed to customers, which is the
  definition the taxonomy uses. Two of them, BLK-05 and BLK-06, came from the
  two internal-FAQ questions that reliably pay: who owns the system this depends on, and can we
  enumerate the affected population retroactively. Both reshaped the release plan.







  §5 — Traceability
  
Every requirement cites the paragraph it came from.

  
Hover a requirement to light up its source. This one rule is what keeps scope honest —
  and it's the mechanism that caught the one requirement everybody wanted.

  

    

      
01-press-release.md · ¶3

      
Ghost Seats closes the loop. Every deprovisioning event now waits on a
      confirmation from each connected integration. Confirmations that arrive within 60 seconds mark the
      event complete. Anything that does not arrive marks the event incomplete and names the integration
      that failed, on the audit entry the admin already reads and in the access-review export they already
      run.

      

      
Caught by the same rule

      

        REQ-DP9 · Force removal from the audit entry
        Source: NONE — FLAGGED, not customer-derived
        
The first thing anyone asks for after seeing the demo, and
        nothing above it asks for it. Held, excluded from every release slice, exported with an
        unsliced label — not deleted. The honest fix is upstream: put remediation in the press
        release, re-run the Stage 1 critic, and let it flow down with a source. That costs a re-review,
        which is exactly why people would rather add it here.

  §6 — Ship it
  
Four vertical slices. Two of them can't be scheduled.

  
Each slice is independently shippable and independently testable, cut by narrowing the
  customer scenario rather than by layer. Six open blockers should produce a plan that is half blocked —
  a plan that isn't is a plan that quietly picked answers.

  
R1 ──▶ R2 ──▶ R3  [BLOCKED BY BLK-05]
 │
 └───▶ R4          [BLOCKED BY BLK-01, BLK-02, BLK-03, BLK-06]

  

    
SliceShipsStatus

    
R1 Confirmation recorded for the highest-volume integration
        Every deprovisioning event on one integration carries a recorded outcome. No customer-facing
        change — ships dark on purpose, because the real failure rate is the input to almost every open
        question.Schedulable

    
R2 The admin sees it
        The audit entry shows per-integration state and never renders an unrun check as complete.
        Schedulable

    
R3 All connected integrations, with honest coverage
        Coverage across every integration; unreachable distinguished from failed; a real baseline.
        Blocked — BLK-05 has no owner

    
R4 Account for what already happened
        The real exposure window, a retrospective report, notification to affected customers.
        Blocked — four blockers, three of which decide whether this slice
        exists in this shape

  than dropped, because a blocked epic in the backlog is the record of why the work stopped.







  §7 — Bring your own context
  
How is this useful when it knows nothing about your business?

  
It works with none and gets materially sharper with each thing you give it. Tick what you
  have. The confidence meter and the critic dimensions update as you go — this is the before/after argument
  in about four seconds.


  
Nothing leaves your browser. Dropping a file here reads its name and
  discards the rest. There is no upload, no parsing, no network request on this page at all. A page that
  appeared to ingest your strategy document would be doing theatre, and you'd spot it.

Six blockers either way. That's the honest
  headline. What changed is the quality of the question: "does
  this match strategy?" became "the pillar says yes and the
  budget line says no — here are both sentences, which wins?" The first needs a meeting to make
  progress. The second one is the meeting agenda. And the run found a conflict — the delivery plan
  needs an integration-agreement change the strategy defers to next year — that the no-context run
  structurally could not have seen.







  §8 — Install
  
Three ways in.

  

    
Plugin marketplace

      
In Claude Code:

      
/plugin marketplace add \
  siddarthnyati/working-backwards

      
/plugin install working-backwards

    
Drop it in

      
No plugin machinery needed — the skill stands alone.

      
cp -r plugins/working-backwards/\
skills/working-backwards \
  ~/.claude/skills/

    
Claude.ai

      
Download dist/working-backwards.skill from the repo and
      upload it in settings. Then attach your context documents to the conversation or the Project — that's
      tier 1.

  

  
Where this isn't useful

  
Single-team, well-understood,
  already-aligned work. That's a ticket, not a discovery session, and running nine stages on it is how
  people conclude the method is overkill and never come back. Use Lightweight mode for a compliance
  mandate where the what is fixed, and don't run Full mode on everything.
