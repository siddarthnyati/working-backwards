# Release plan — Silent Step-Down

Four vertical slices, cut by narrowing the scenario. The Stage 7 critic caught REQ-DP4
initially placed in two slices — the reconciliation check exists for exactly that; see
`DECISIONS.md`.

## Slices

```
R1 · Record everything, show nothing
Requirements: REQ-D1, REQ-D2
Depends on: —
Blocked by: —
Ships: every transaction carries an authentication outcome; step-downs classified incident vs pattern-suspicious. Dark — no merchant-facing change.
Independently testable: yes
Test harness:
  - Timeout injection: force an auth timeout; assert stepped-down recorded before authorization proceeds
  - Path audit: static check that no branch reaches authorization without an outcome write
  - Classification: seeded incident cluster and seeded merchant-concentrated series label correctly
Why first: the recorded outcome is the input to visibility, policy, telemetry M1-M6, and the fraud question. And it establishes the true step-down floor (IFAQ-08).
```

```
R2 · The merchant sees it
Requirements: REQ-DP1, REQ-DP2
Depends on: R1
Blocked by: —
Ships: outcome field in reporting and API; same-day digest with incident grouping.
Independently testable: yes
Test harness:
  - Field parity: recorded event and API/reporting field match on all four outcomes
  - Digest grouping: 400 incident step-downs render one line; 3 unrelated render three rows
  - Visibility lag under 24h on seeded events (M3)
```

```
R3 · The merchant decides
Requirements: REQ-DP3, REQ-DP5, REQ-DP4
Depends on: R2
Blocked by: BLK-02, BLK-06
Ships: policy control with allow/block live for all merchants; require-exemption if BLK-02 permits; no silent path anywhere.
Independently testable: yes
Test harness:
  - Policy block: timeout produces authentication-unavailable decline, outcome attempted
  - Policy-service failure: outcome stepped-down / policy-unavailable, never silent, never completed
  - Distinct decline reason survives acquirer response-code mapping (Q-07)
Not schedulable: BLK-02 shapes whether require-exemption exists; BLK-06 owns the conversion-vs-liability launch comms. Allow/block could ship without the third option if BLK-02 resolves negatively — that fork is the plan's main open decision.
```

```
R4 · Account for the past
Requirements: REQ-D3, REQ-D4
Depends on: R1
Blocked by: BLK-01, BLK-05
Ships: historical enumeration joined to chargebacks; the measured fraud differential (M6); the evidentiary input to any restitution decision.
Independently testable: yes
Test harness:
  - Join over seeded history returns chargeback outcomes per stepped-down transaction
  - Ranges predating retention state so explicitly
  - M6 report includes populations and period; refutation path for C5 recorded
Rests on assumption: REQ-D4 rests on C5 (Q-04)
Not schedulable: BLK-05 decides whether this slice can exist as specified; BLK-01 decides what it is for.
```
